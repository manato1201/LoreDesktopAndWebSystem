# 06. 差分(diff)のアルゴリズム

**この章で分かること**: 「2つのテキストの違い」を、どうやって求めるか。**最長共通部分列(LCS)**を表で手計算し、diff を自作して、実際の API(`similar` クレート)と見比べます。

前提: [05](05-content-addressing.md)(コミットと内容のハッシュ)。

## 6.1 diff とは何か

2つのファイル(行の並び)が与えられたとき、**古い方を新しい方に変えるための、最も少ない編集**(行の削除と挿入)を求めるのが diff です。

```
古い:  A B C D E          新しい:  A C D X E

 A         (そのまま)
-B         (削除)
 C         (そのまま)
 D         (そのまま)
+X         (追加)
 E         (そのまま)
```

「最も少ない編集」を求めることは、「**両方に、同じ順序で現れる行をできるだけ多く**見つけること」と同じです。変わらなかった行を最大にすれば、編集が最小になるからです。これが**最長共通部分列(LCS: Longest Common Subsequence)**です。

> **部分列とは**: 元の並びから、順序を保ったまま(連続でなくてもよい)いくつか取り出したもの。`A C D E` は `A B C D E` の部分列。

## 6.2 LCS を表で解く(動的計画法)

2つの列 `a`(古い)と `b`(新しい)で、表 `t[i][j]` を「`a` の先頭 `i` 個と `b` の先頭 `j` 個の LCS の長さ」と決めます。

- 末尾の要素が**同じ**なら、`t[i][j] = t[i-1][j-1] + 1`(その要素を共通部分列に足す)
- **違う**なら、`t[i][j] = max(t[i-1][j], t[i][j-1])`(どちらかを諦める)

```
       -  A  C  D  X  E        ← b(新しい)
 -     0  0  0  0  0  0
 A     0  1  1  1  1  1
 B     0  1  1  1  1  1
 C     0  1  2  2  2  2
 D     0  1  2  3  3  3
 E     0  1  2  3  3  4        ← 右下の 4 が LCS の長さ(A C D E)
 ↑
 a(古い)
```

右下の **4** が答えです(共通の行が4つ → 変わった行は、削除1・追加1)。

### 表を埋める手順の例

`t[3][2]`(`a` の `A B C` と `b` の `A C`)を考えます。末尾は `C` と `C` で同じなので、`t[2][1] + 1 = 1 + 1 = 2`。表の `C` 行・`C` 列が `2` になっています。

## 6.3 diff を作る(戻りながら読む)

表ができたら、右下から**左上へ戻り**ながら、どの行を残し/消し/足したかを読みます。

```python
def lcs_table(a, b):
    t = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            if a[i - 1] == b[j - 1]:
                t[i][j] = t[i - 1][j - 1] + 1
            else:
                t[i][j] = max(t[i - 1][j], t[i][j - 1])
    return t


def diff_lines(a, b):
    t = lcs_table(a, b)
    out = []
    i, j = len(a), len(b)
    while i > 0 or j > 0:
        if i > 0 and j > 0 and a[i - 1] == b[j - 1]:
            out.append((" ", a[i - 1]));  i -= 1; j -= 1          # そのまま
        elif j > 0 and (i == 0 or t[i][j - 1] >= t[i - 1][j]):
            out.append(("+", b[j - 1]));  j -= 1                  # 追加
        else:
            out.append(("-", a[i - 1]));  i -= 1                  # 削除
    out.reverse()
    return out


for sign, line in diff_lines(list("ABCDE"), list("ACDXE")):
    print(sign, line)
```

実行すると、冒頭の結果が出ます。

```
  A
- B
  C
  D
+ X
  E
```

この関数を、ランダムな500組の入力で検証しました。性質は次の3つで、いつでも成り立ちます。

1. `-` の行を**除いた**ものが、新しい列になる。
2. `+` の行を**除いた**ものが、古い列になる。
3. 変わらなかった行の数が、LCS の長さと等しい。

> **性質で検証する**: 「具体例を1つ」だけでなく、「**どんな入力でも成り立つ性質**」を乱数で試す方法(プロパティテスト)は、アルゴリズムの確認にとても強力です。

## 6.4 計算量と、実際のアルゴリズム

表は `(a の行数) × (b の行数)` 個のマスを持つので、時間も記憶も **O(N × M)** です。1万行 × 1万行なら 1億マスで、重すぎます。

実用の diff(Git も `similar` も)は、**Myers のアルゴリズム**(1986)の系統です(`similar` の既定は `Algorithm::Myers`。ほかに Patience・LCS の表方式・Hunt・Histogram も選べます)。考え方は次のとおりです。

```
編集グラフ: 横に進む = 古い行を削除 / 縦に進む = 新しい行を追加 / 斜めに進む = 一致(タダ)
            左上 → 右下 への、斜めをできるだけ使う「いちばん安い道」を探す
```

- 変更が少ない(D が小さい)ときほど速く、時間は **O((N+M) × D)**。ほとんど同じ2つのファイルなら、ほぼ線形です。
- 表を全部は持たず、「各対角線で、いちばん先まで進めた位置」だけを覚えます。

**実際の使用**: `get_diff` は `similar::TextDiff::from_lines`(既定が Myers)を呼ぶだけです。自作する必要はありませんが、**仕組みを知っていると、挙動の「なぜ」が分かります**(次の節)。

## 6.5 diff の答えは、1つとは限らない

```python
diff_lines(list("ABAB"), list("BABA"))
# [('-','A'), (' ','B'), (' ','A'), (' ','B'), ('+','A')]    ← 先頭の A を消して、末尾に A を足す
```

LCS は `B A B`(長さ3)で、編集は2回(削除1・追加1)。もう一つ、「先頭に B を足し、末尾の B を消す」も**同じ回数**の正解です。どちらを選ぶかは、実装の「同点のときの決め方」で変わります。

> **ここから分かること**: diff の結果は「**最小の編集の1つ**」であって、「唯一の正解」ではありません。テストで diff の**行をそのまま**比べると、実装やバージョンの違いで壊れます。**性質**(6.3 の3つ)で確かめるほうが、堅牢です。

## 6.6 このシステムの diff エンドポイント

```
GET /api/repositories/{slug}/diff/{*path}?from={コミットのハッシュ}&to={コミットのハッシュ}
```

[`handlers.rs`](../../lorehub-api/src/handlers.rs) の `get_diff` が処理します。流れは次のとおりです。

1. リポジトリが無ければ **404**。そのパスの **Read 権限**が無ければ **403**(`get_file_content` と同じ関門)。
2. `from` と `to` が両方必要(無ければ **400**)。どちらかのコミットが存在しなければ **404**。
3. **各コミット時点で、そのパスの内容のハッシュ**を調べる(`tree_entries` を引く)。
   - どちらにも無い → 404 / `to` にだけある → **added** / `from` にだけある → **deleted** / 両方にあって同じ → **unchanged** / 違う → **modified**
4. `isBinary` は**ファイルの種類**(拡張子から決まる `file_kind`)で決める。`"text"` だけが diff の対象。
5. **テキストで modified のときだけ**、2つのブロブを読み、`TextDiff::from_lines` で行の差分を作る。それ以外は `lines: null`。
6. どちらかが **5 MiB** を超えると 400(巨大な「テキスト」は、たいてい誤判定のバイナリ。メモリも守る)。

応答の形(`models.rs` の `FileDiff` / `FileDiffLine`):

```json
{
  "path": "Source/Game.cs",
  "fromHash": "…", "toHash": "…",
  "changeType": "modified",
  "isBinary": false,
  "lines": [
    { "type": "context", "text": "using System;", "oldLine": 1, "newLine": 1 },
    { "type": "remove",  "text": "int speed = 5;", "oldLine": 4, "newLine": null },
    { "type": "add",     "text": "int speed = 8;", "oldLine": null, "newLine": 4 }
  ]
}
```

- `remove` は `newLine` が無く、`add` は `oldLine` が無い。`context` は両方ある。
- 行の比較は**改行文字を含めて**行う(`from_lines` は改行を保ったまま行に分ける)。返す `text` からは、行末の改行(`\n`、`\r`)を取り除く(`trim_end_matches`)。そのため、**改行コードだけが違う行**(LF → CRLF に変換したファイルなど)は、表示は同じ文字なのに「変更あり」として検出される。
- 文字コードは `from_utf8_lossy`(不正なバイトは `�` に置き換え)で読む。

> **注意**: Web の PR 画面は、この `diff` エンドポイントではなく、**PR に埋め込まれた差分データ**(`PullRequest.changed_files`)を表示しています。2つは別の仕組みです(`models.rs` の `FileDiff` の説明を参照)。PR の差分を実際の diff にする作業は、将来の課題です。

## 6.7 表示: 色だけに頼らない

Web の差分ビューア(`TextDiffViewer`)は、`+` と `−`(本物のマイナス記号)を**行の頭に必ず**出します(`lib/change-symbols.ts`)。背景の緑・赤を消しても、追加と削除が区別できます([09章](09-ui-rules.md))。

## 6.8 まとめ

- diff = 古い列を新しい列にする最小の編集 = **LCS** を求めること。
- LCS は、表(動的計画法)で解ける。O(N×M)。
- 実用の diff は Myers 法の系統。変更が少ないほど速い(O((N+M)D))。
- 答えは1つとは限らない。テストは**性質**で書く。
- このシステムでは、テキストで modified のときだけ行の差分を作り、バイナリは種類だけを返す。

## 6.9 演習

1. 6.3 のコードを手元で動かし、`diff_lines(list("kitten"), list("sitting"))` の結果を、表を自分で書いて**手計算と一致**させる。
2. `diff_lines` を改造して、`oldLine` / `newLine`(1始まり)を各行に付ける。`context` は両方、`remove` は `oldLine` だけ、`add` は `newLine` だけ。API の形と同じになることを確かめる。
3. **計測**: 行を1000、3000、5000と増やして(ほとんど同じ2つの列)実行時間を測る。表の方式が O(N×M) になっていること、「ほとんど同じ」でも速くならないことを確かめる。Myers 法が有利な理由を、自分の言葉で説明する。
4. 行単位でなく**単語単位**の diff にするには、何を変えればよいか。(ヒント: 列の要素を「行」から「単語」にするだけ。`similar` には `TextDiff::from_words` がある。)
5. **API を使う**: ログインして、`starforge-vfx` のコミット2つを選び、テキストファイルの `diff` を `curl` で取る。`lines` の `oldLine`/`newLine` が、2のあなたの出力と一致するか確かめる。(`GET /commits` で2つのハッシュを、`GET /tree` でテキストのパスを探す。)
