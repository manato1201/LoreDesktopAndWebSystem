# 10. アルゴリズム集

**この章で分かること**: このシステムに実際に入っている小さなアルゴリズムを、1つずつ「何を解いているか → 考え方 → 実コード → 動かして確認 → 限界」の順に読みます。どれも数十行ですが、**木・グラフ・再帰・丸め**という、よく出る道具の見本です。

前提: [02](02-rust-basics.md)(再帰・イテレータが読める)。Python の移植版は、手元で実行して確かめたものです。

## 10.0 計算量の読み方(最初に)

| 記法 | 入力が10倍になると | 例 |
|---|---|---|
| O(1) | 変わらない | `shortHash`(先頭7文字を切る) |
| O(log n) | ちょっと増える | 整列済みの `BTreeMap` の検索 |
| **O(n)** | 10倍 | ツリーの全ファイルを1回なでる |
| O(n log n) | 10〜30倍 | 整列(`sort`) |
| **O(n²)** | **100倍** | 二重ループ。1万件で1億回 |

「N」が何かを、必ず言います。ファイル数か、コミット数か、行数か。

## 10.1 木(トライ)で、パスの一覧を階層に直す

**解く問題**: `GET /tree` は、ファイルのパスの**平らな一覧**(`Assets/Characters/hero.fbx`, …)を、画面用の**入れ子の木**にして返します。

**考え方**: パスを `/` で区切り、1区切りずつ降りながら、無ければフォルダを作ります(トライ木)。最後に、フォルダ→ファイルの順、名前順に並べます。

```python
def build_tree(paths):
    root = {}
    for path in paths:
        *dirs, name = path.split("/")
        node = root
        for d in dirs:
            node = node.setdefault(d, {})        # フォルダ(無ければ作る)
        node[name] = None                         # ファイル
    # ... フォルダ→ファイル、名前順に並べて、{kind,path,name,children} に変換
```

実コードは [`vcs_store.rs`](../../lorehub-api/src/vcs_store.rs) の `build_tree`(`BTreeMap` が自動で名前順にする)です。入力と出力の例:

```
入力: Assets/Characters/hero.fbx, Assets/Characters/rig.fbx, Assets/props.txt, README.md, Docs/a.md

出力:  Assets            ← フォルダが先、名前順
         Characters
           hero.fbx
           rig.fbx
         props.txt
       Docs
         a.md
       README.md         ← ファイルは後
```

- **計算量**: 全パスの区切りの総数に比例(O(総文字数 × log 子の数))。
- **細部**: ファイルと同じ名前のフォルダが同時にある(`Foo` と `Foo/Bar`)状況は、実データでは起きません。それでも**パニックせず、黙って捨てる**実装になっています(読み取りの経路は落とさない、という判断)。コードのコメントを読んでください。
- **Web 側の再帰**: `lib/tree-utils.ts` の `findNode`(木を深さ優先で探す)と `directoriesOnly`(フォルダだけを残す)も、同じ「子に同じ関数を呼ぶ」再帰です。

```ts
export function findNode(nodes: TreeNode[], path: string): TreeNode | undefined {
  for (const node of nodes) {
    if (node.path === path) return node;
    if (node.kind === "directory") {
      const found = findNode(node.children, path);     // ← 子の木で、同じ関数を呼ぶ
      if (found) return found;
    }
  }
  return undefined;
}
```

**再帰を読むコツ**: ①終わる条件(見つかった/子が無い)、②自分より**小さい**問題(子の木)に同じ関数を呼ぶ、の2つを探す。

## 10.2 パスの祖先を、近い順に列挙する

**解く問題**: パスACL([07](07-auth-and-authz.md))は「パスと、その祖先を、具体的な順に」見ます。

```
"Assets/Characters/hero.fbx"  →  [ "Assets/Characters/hero.fbx", "Assets/Characters", "Assets" ]
```

**考え方**: 最後の `/` より後ろを切り落とす、を繰り返します([`authz.rs`](../../lorehub-api/src/authz.rs) の `path_ancestors`)。

```python
def path_ancestors(path):
    out, cur = [], path
    while True:
        out.append(cur)
        i = cur.rfind("/")                 # 最後の "/" の位置
        if i == -1:
            return out                     # もう親が無い
        cur = cur[:i]                      # そこまでに切り詰める
```

- **計算量**: パスの深さに比例(O(深さ))。深さは数個なので、実質 O(1)。
- **境界**: `README.md`(区切りなし)は `["README.md"]` 1件。**空文字のルート `""` は含めません**(`access_entries` のキーに `""` は無いため)。

## 10.3 コミットの履歴を、レーンに並べる(グラフの配置)

**解く問題**: コミット一覧を、ブランチごとの**横線(レーン)**に並べて描きます。`BranchGraph` が使う `buildCommitGraph` ([`graph-layout.ts`](../../lorehub-web/src/lib/graph-layout.ts))。

**考え方**(単純で、うまくいく範囲が決まっている):

1. **x** = コミットの**並び順**(古い順の位置)。時刻の長さではなく、等間隔。
2. **レーン** = **ブランチ名**ごとに1本。デフォルトブランチが 0 番、ほかは**初めて現れた順**に次の番号。
3. **辺** = 各コミットから、**親のコミット**へ(親のハッシュをマップで引く)。

実際のコードを、小さな履歴で動かした結果です。

```
main:  c1 - c2 - c3 ------ c6
              \
feat:          c4 - c5

c1  x=0  lane=0       c4  x=3  lane=1
c2  x=1  lane=0       c5  x=4  lane=1
c3  x=2  lane=0       c6  x=5  lane=0
edges:  c1->c2  c2->c3  c2->c4  c4->c5  c3->c6
laneCount: 2   laneStatus: {"0":"trunk", "1":"open"}
```

- **計算量**: コミット数を n として **O(n)**(`Map` で親を引くので、二重ループにならない)。
- **前提**(コードのコメントにある): ①入力は**古い順**で、②どの親も**自分より前**に出てくる。順序が崩れると、親が見つからず辺が欠ける。**前提を、呼ぶ側が守る**設計。

**限界と、演習の種**:

- レーンは**再利用しない**(ブランチが100本あれば100本の線)。終わったブランチのレーンを空けて詰める(区間の貪欲法)と、省スペースにできる。
- `laneStatus` の `"merged"`(「どこかのレーンへ辺が出ている」)は、**単一の親しか持たない今のモデルでは、実データに現れません**。マージコミット(親が2つ)が無いため、レーン1 から別レーンへ辺が出ないからです。以前の「2親のマージコミットを含む模擬データ」の名残で、**今は到達しない状態**になっています(凡例に「Merged」が出ているのは、その名残)。使われない分岐を見つけたら、**消すか、残す理由を書く**のが保守です。

## 10.4 相対時刻と、容量の表記(そして、丸めの罠)

### 相対時刻(バケット化)

[`vcs_store.rs`](../../lorehub-api/src/vcs_store.rs) の `format_relative_time`: 経過秒を、決まった区間に入れて、その区間の単位で数えます。

```
60秒未満 → "just now"   /  1時間未満 → "N m ago"  /  1日未満 → "N h ago"
1週間未満 → "N d ago"    /  それ以上 → "N w ago"
```

```
      60s -> 1m ago     3599s -> 59m ago     3600s -> 1h ago
    86399s -> 23h ago   86400s -> 1d ago    604800s -> 1w ago
```

**区間の境目**(59→60、3599→3600)で**切り捨て**になる点に注意。「1時間59分」は「1h ago」です。**精度を捨てて、読みやすさを取る**設計。**月・年は無く**、`1209600s` は `2w ago`、半年前でも `26w ago` と出ます(限界)。

### 容量の表記と、丸めの罠(実際にあった不具合)

`format_size_label` は、バイト数を `KB`/`MB`/`GB` にして、小数1桁で出します。最初の実装は、**単位を先に選んで、あとで丸めて**いました。

```
1048575 B = 1023.999 KB  →  先に単位を選ぶ(KB)  →  丸める  →  "1024.0 KB"   ← 間違い。"1.0 MB" が正しい
```

```
      B    修正前         修正後
 1023   1023 B       1023 B
 1048575  1024.0 KB     1.0 MB       ← 修正で変わる
 1073741823 1024.0 MB    1.0 GB
```

**教訓**: **「丸めた後の値」で境界を判定する。** 丸める前に単位を決めると、丸めで境界を超えたとき、桁が合わなくなります。修正は、丸めた値が 1024 に達したら、1つ上の単位に上げる(Rust と TypeScript の両方、テスト付き)。

> **同じ不具合を2か所で作っていた**ことも教訓です。API(Rust)と Web(TypeScript)は、**別々に同じ関数を書いて**います。片方を直しても、もう片方は残ります。「同じことを2言語で実装している」場所は、**両方を同時に直す・テストする**必要があります(第13章のチェックリスト)。

## 10.5 容量の集計(再帰と、不変条件)

`summarizeStorage`([`lib/format.ts`](../../lorehub-web/src/lib/format.ts)): ツリーを再帰でなでて、ファイルの種類ごとに `sizeBytes` を足します。

```ts
const walk = (nodes: TreeNode[]) => {
  for (const node of nodes) {
    if (node.kind === "directory") walk(node.children);          // フォルダ: 中へ
    else sums[BUCKET_OF_KIND[node.kind]] += node.sizeBytes;      // ファイル: 種類のバケットへ足す
  }
};
```

- **不変条件**(いつでも成り立つ約束): **合計 = 各バケットの和**。合計を別に数えず、**バケットから作る**ので、バーと数字が食い違えません。`format.test.ts` が、これをテストしています。
- 種類の対応は、`BUCKET_OF_KIND` の表で決める(`text` と `binary` は「その他」)。**新しい種類を足すとき**、この表に足し忘れると TypeScript が**コンパイルエラー**にしてくれる(`Record<FileKind, ...>` なので)。型で、足し忘れを防ぐ例。

## 10.6 再帰で木を描く(決定的な擬似乱数)

空のリポジトリと 404 の「アスキーの木」([`lib/ascii-tree.ts`](../../lorehub-web/src/lib/ascii-tree.ts))は、**再帰で枝分かれ**させて描いています。

```
grow(x, y, 角度, 長さ, 深さ):
    角度の向きに、長さぶんの線を引く
    深さ == 0 なら、先端に葉を散らして終わり
    そうでなければ、先端から 左右 に「少し短い枝」を2本(奇数の深さでは、まっすぐな3本目も)出す
```

- **深さ4**から始めると、枝(線分)は全部で**57本**(深さ0=1、深さ1=4、深さ2=9、深さ3=28、深さ4=57)。**深さが1つ増えるごとに約2〜3倍**になる(指数的な増え方。深さを大きくすると、すぐ重くなる)。
- **セル(文字)の縦横比**: 端末の1文字は縦に長い(約 2:1)ので、横方向の進みを2倍にして、角度が正しく見えるようにしている。
- **擬似乱数は、固定の種(seed)で決定的に**(`mulberry32`)。**毎回まったく同じ絵**になるので、サーバーとブラウザで描画が食い違わず(React の「不一致」エラーを避けられ)、テストもできます。

```ts
function createRandom(seed: number) {
  let state = seed | 0;
  return () => {
    state = (state + 0x6d2b79f5) | 0;                    // 状態を進める
    let t = Math.imul(state ^ (state >>> 15), 1 | state);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;        // [0, 1) の小数
  };
}
```

> **「ランダム」を、再現できるようにする**のは、テストとデバッグの基本です。`Math.random()` を直接使うと、失敗が再現できません。

## 10.7 順序に依存しないハッシュ(正規化)

[05](05-content-addressing.md) の `compute_commit_hash`: ステージした順序で結果が変わらないよう、**パスを昇順に並べてから**ハッシュします。「**同じ意味なら同じ表現**にする」(正規化)は、ハッシュ・キャッシュのキー・比較の前に、よく必要になります。

## 10.8 まとめ

| 場所 | 道具 | 計算量 | 注意 |
|---|---|---|---|
| `build_tree` | トライ木 | O(総文字数) | 衝突するパスは捨てる |
| `path_ancestors` | 区切りを削る | O(深さ) | ルートの `""` は含めない |
| `buildCommitGraph` | `Map` + 1回走査 | O(n) | 入力は古い順、親は前。`merged` は到達しない |
| `format_relative_time` | 区間分け | O(1) | 月・年が無い。切り捨て |
| `format_size_label` | 単位の繰り上げ | O(1) | **丸めた後で境界を判定** |
| `summarizeStorage` | 再帰 | O(n) | 合計はバケットから作る |
| `buildAsciiTree` | 再帰+固定シード | 枝の数 | 深さで指数的に増える |

## 10.9 演習

1. 10.1 の `build_tree` を、手元の Python で動かして、`Docs/a.md` を `docs/a.md`(小文字)に変えたとき、並び順がどうなるか確かめる。(ヒント: 大文字が小文字より前。`BTreeMap` もバイト順。人が期待する順と違う場合、何をすべきか。)
2. 10.3 の `buildCommitGraph` を、`laneStatus` が `"merged"` になる**入力**(親が別レーンのコミット)を作って、実際に動かす。その入力は、今の API では作れるか?(ヒント: `create_commit` の親は、どう決まるか。)
3. **改善**: レーンの再利用を実装する。「ブランチの最後のコミットの x」を覚えておき、それより後に始まるブランチには、空いたレーンを割り当てる。何がレーンの本数の下限か?(同時に生きているブランチの最大数。)
4. 10.4 の `relative_time` に「月」「年」を足す。境界(30日、365日)の取り方で、「1か月前」と「4w ago」が食い違わないようにするには?
5. `format_size_label` に、**TB** を足す。丸めの繰り上げ(`1024.0 GB` → `1.0 TB`)は、どう書けばよいか。Rust と TypeScript の**両方**に足し、両方にテストを書く。
6. `buildAsciiTree` の `SEED` を変えて、木の見た目がどう変わるか見る(`node --experimental-strip-types -e "import('./src/lib/ascii-tree.ts').then(m=>console.log(m.ASCII_TREE))"`)。気に入った種を選ぶ。**テスト**(`ascii-tree.test.ts`)は、種を変えても通るか?通らないなら、なぜか(テストが絵の**性質**でなく**中身**に依存していないか)。
