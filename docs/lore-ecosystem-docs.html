04 / Data Flow

認証シーケンス

Server Componentはブラウザとは別プロセスのため、受信したCookieを手動でAPIリクエストへ転送する必要がある — この非対称性がこのアーキテクチャの要点。

Browser → Web
/login で email / password を送信(Client Component)
Web → API
POST /api/auth/login(credentials: include)
API
argon2でパスワード検証 → セッション発行
Set-Cookie: lorehub_token(HttpOnly, SameSite=Lax, 7日)
Browser → Web(SSR)
以降のページ遷移: GET /repositories/xxx
Web(Server Component)
cookies() からセッションCookieを取得
ブラウザのCookieジャーとは無関係な別プロセス
Web → API
Cookieヘッダを明示的に転送して再フェッチ
これを忘れると SSR は常に401になる
05 / State

データモデル(AppState、非VCS)

PR一覧・監査ログ・組織メンバー・招待・パスワードリセット等の非VCSデータは正規化せず、フィールドごとに1つのJSONブロブとして kv_store に保存(意図的なトレードオフ、詳細は技術資料 §5)。VCSデータ(Repository・コミット・ブランチ・ツリー)は実コンテンツアドレス方式の正規化SQLテーブルとして別管理(次節参照)。

PullRequest
  • id, repo_slug, status
  • diff_files
  • comments
OrgMember
  • email, name, role
  • password_hash
AuditLogEntry
  • actor, action
  • target, timestamp
InviteEntry / PasswordResetEntry
  • email, role, teams
  • expiresAt
05.5 / VCS

VCSスキーマ(正規化SQLテーブル)

以前は全リポジトリで共有される静的シードデータでしかなかったコミット/ブランチ/ツリーを、実SHA-256ハッシュ・単一親コミット・重複排除されたコンテンツアドレスblobストレージへ全面再設計した。全ての repo_slug 外部キーが ON DELETE CASCADE——リポジトリ削除1操作で関連データが原子的に全消去される。正確なスキーマは lorehub-api/migrations/0001_vcs_schema.sql を参照。

repositories
  • slug (PK)
  • visibility
file_blobs
  • repo_slug, content_hash (PK)
  • size_bytes
branches
  • repo_slug, name (PK)
  • head_commit_hash → commits
commits
  • repo_slug, hash (PK)
  • parent_hash(単一親)
commit_files
  • commit_hash, path (PK)
  • change_type, content_hash
tree_entries
  • commit_hash, path (PK)
  • content_hash → file_blobs

current_branch(現在ブランチ)・staged_content(未コミットの作業コピー)・pending_changes(ステージ済み変更)・file_locks(排他ロック)も同じrepositories配下に存在するが、上のカードでは省略。ファイル実体そのもの(バイト列)はDBの外、ファイルシステム上の blobs/<repo_slug>/<hash> に content-addressed で保存される(blob_store.rs)。

05.7 / AuthZ

認可とセキュリティ

access_entries(パス別ACL)は設定自体は以前から存在したが、実際にはどのハンドラからも参照されず、認証さえ通れば誰でも任意のパスを読み書きできた。authz.rsのcheck_path_permissionがこれを実強制するようになった。

Step 1
Owner/Adminロールなら常に許可
Step 2
パスの祖先を最も具体的な順に走査
例: Assets/Characters/hero.fbx → Assets/Characters → Assets
Step 3
最初にエントリを持つ祖先が確定 — それより上位の祖先は一切参照しない
Step 4
principalが一致し必要な権限を含むかで許可/拒否
どの階層にもエントリが無ければデフォルト許可(既存デモパスの挙動を維持)

組織操作(リポジトリ削除・メンバーのロール変更・ACL一括Apply・招待の作成/一覧/取り消し)はこのパスACLとは独立に、Owner/Adminロールのみに制限するRBACゲートを別途通過する。ネットワークレベルでは、既定でSecure属性つきCookie・LOREHUB_WEB_ORIGIN単一オリジンのCORS・リクエストボディ上限(既定48MiB)・ログインの送信元IP単位レート制限(バースト8回+60秒に1回補充)を追加した。

07 / Reference

08.5 / Ops

デプロイ・観測性

docker-compose.ymlでlorehub-api・lorehub-webの2サービスを構成。実際にVercel + Cloudflare Quick Tunnelへデプロイした際、クロスドメイン特有のCookie問題を発見・修正した。

Local / Compose

同一ホスト名配置

localhost:3000 / localhost:4000
  • ブラウザ視点では同一サイト扱い、Cookieは無条件に機能
  • named volume 1つに lorehub.db + blobs/ の両方
  • GET /api/health をDockerのHEALTHCHECKが使用
Cross-domain

Vercel + トンネル配置

実デプロイで発見した問題
  • APIのCookieはAPI自身のドメインにしか保存されない
  • CORS/SameSiteでは解決不可(そもそもフロントエンド側にCookieが無い)
  • next.config.ts の rewrites() でサーバーサイド転送し解決
  • NEXT_PUBLIC_USE_API_PROXY=true でブラウザ側を相対パスへ切替
Observability

メトリクス・ログ

運用可視性
  • GET /metrics(Prometheusテキスト形式)
  • method/route/statusごとのリクエスト数+レイテンシヒストグラム
  • LOREHUB_LOG_FORMAT=json で構造化ログ
  • GitHub Actions CI(cargo test/clippy/fmt + npm build/lint/test)

詳細なデプロイ手順・環境変数・バックアップ方法は docs/DEPLOYMENT.md、デスクトップインストーラーのビルドは docs/DESKTOP_PACKAGING.md を参照。

10 / Workflow

マルチエージェント並行開発

ディレクトリが重ならない3つの作業を分割し、バックグラウンドサブエージェントとして並行実行した。

Main session
lorehub-web/ — リポジトリ設定機能(直接実装)
Main session
loreforge-client/ — コミット履歴ビュー(sub-agent)
Main session
loreforge-server-admin/ — 権限設定永続化(sub-agent)

鍵となったのは「スコープの分離」(ディレクトリが衝突しない)と「知識の伝播」(1体目が発見した罠 — QML singleton、SendInputの不通、QStringLiteralの制約など — を後続のプロンプトに引き継いだこと)。

11 / Trust

独立再検証パターン

Phase 7ではサブエージェントの完了報告を鵜呑みにせず、オーケストレーターが毎回ゼロから独立して再現するルールを徹底した。

Step 1
build/ を完全削除してクリーンビルド
Step 2
報告内容を見ずに、報告された動作を自分の手で再現
Step 3
一次証拠を取得
実プロセスのPID・tasklist出力・HTTPレスポンスの実バイト数・Windowsレジストリの値そのもの
Step 4
TEMP-VERIFY タグの検証用コードが完全除去されているか grep で確認

この過程で、報告だけでは分からない環境ドリフト(Visual Studioのインストールパスがセッション中に 2022 フォルダから 18 フォルダへ自動更新されていた)や、検証手法自体の欠陥(QMLの console.log がリダイレクトログへ確実にフラッシュされない、複雑な画面遷移よりC++側の単機能を直接検証する専用QMLの方が確実)を発見した。
